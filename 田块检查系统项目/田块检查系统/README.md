# 田块监测系统

基于 C 语言的实验田传感器监测与告警管理程序（实训项目）。使用链表管理田块、传感器记录与告警，覆盖田块管理、记录展示、告警生成与排序、趋势分析等模块。

## 项目功能

- **田块管理**：添加新田块、按名称搜索、按负责人搜索
- **传感器记录**：添加传感器记录、展示最新记录、展示指定田块全部记录
- **告警模块**：单条温湿度异常告警、连续异常告警、按严重等级降序展示
- **趋势分析**：分析田块温度变化趋势

## 问题一：告警严重等级判断逻辑与实训文档要求不符

**【问题】**：告警模块的严重等级赋值逻辑错误，未严格按照实训项目文档规定的告警等级规则实现。

**【现象】**：温度＞35℃或＜10℃应为2级告警，湿度＜40%或＞85%应为1级告警，连续3条异常应为3级告警；但实际运行中，单条温湿度异常告警的等级分配错乱，且当温度和湿度同时异常时，只能识别其中一类异常，另一类被覆盖丢失。

**【排查与原因】**：`check_and_generate_alerts` 函数中使用 `param_error` 变量记录异常类型，该变量在温度判断和湿度判断中被重复赋值，导致同时异常时只能保留最后一次判断结果；此外代码自行新增了 `temp_extreme` 和 `hum_extreme` 极端阈值判断（温度0/40、湿度20/95），属于题目未要求的额外业务规则，与文档规定的告警等级体系冲突，最终导致等级分配逻辑混乱。

**【解决方案】**：删除代码中自行新增的极端温湿度阈值判断逻辑；使用独立的标志位（如 `temp_abnormal`、`hum_abnormal`）分别记录温度和湿度异常状态，避免变量覆盖；严格按照文档规则赋值：高低温告警设为2级，高低湿告警设为1级，连续3条异常设为3级；温湿度同时异常时分别生成两条独立告警。

**【经验总结】**：业务逻辑开发必须严格对照需求文档，不能自行增加文档未规定的规则；多个状态同时存在时，应使用独立标志位分别记录，避免单一变量被重复覆盖导致信息丢失。

## 问题二：告警列表未按严重等级降序排序

**【问题】**：告警展示功能未实现按严重程度降序排序的要求，且缺少题目要求独立实现的 `sort_alerts_by_severity` 函数。

**【现象】**：实训文档明确要求告警展示按严重程度降序（3级在前，1级在后），但实际运行中告警列表仅按时间戳倒序输出，高等级告警不一定排在前面；代码中也不存在独立的按告警等级排序的函数。

**【排查与原因】**：`display_all_alerts` 函数中仅对复制的临时告警链表执行了基于时间戳的冒泡排序，排序条件只比较 `timestamp` 字段，完全没有涉及 `severity` 字段；项目未按文档要求单独封装 `sort_alerts_by_severity(Alert *head)` 函数，排序逻辑散落在展示函数内部，且排序维度单一。

**【解决方案】**：独立实现 `sort_alerts_by_severity` 函数，采用冒泡排序对告警链表按 `severity` 字段降序排列，等级相同时再按时间戳倒序排列；在 `display_all_alerts` 中调用该函数对临时链表排序后再输出；同时考虑对原告警链表本身维护等级顺序，而非仅在展示时临时排序。

**【经验总结】**：多维度排序需求应明确优先级，先按主关键字排序，主关键字相同时再按次关键字排序；文档明确要求独立实现的函数应单独封装，不应将逻辑散落在其他函数中，便于复用和测试。

## 问题三：持续异常告警重复生成

**【问题】**：持续环境异常告警存在重复生成问题，同一连续异常场景会产生大量重复告警。

**【现象】**：当某田块连续出现3条及以上异常记录时，每新增一条异常记录就会新生成一条"持续环境异常"告警，导致告警列表中出现多条内容完全相同的持续异常告警，无法区分是否为同一次持续异常事件。

**【排查与原因】**：`add_sensor_record` 每次调用都会触发 `check_continuous_abnormal_alerts`，该函数只要检测到连续异常数≥3就直接调用 `add_alert` 生成新告警，没有先查询该田块是否已经存在未处理的同类型持续异常告警，缺少去重判断逻辑；同时没有记录上一次持续告警的起始时间或事件标识，无法判断是否为同一次连续异常事件。

**【解决方案】**：在生成持续异常告警前，先遍历告警链表检查该田块是否存在未处理（`resolved=0`）的持续异常告警，若存在则不重复生成；可以为持续异常告警增加事件标识字段，或通过判断连续异常的起始记录是否已被覆盖来区分新旧事件；连续异常结束后（出现正常记录）再允许下一次持续异常生成新告警。

**【经验总结】**：基于状态触发的告警必须考虑去重机制，避免同一事件被反复触发；设计告警系统时应区分"事件首次触发"和"事件持续中"两种状态，只有首次触发时才生成告警。

## 问题四：传感器记录展示排序顺序颠倒

**【问题】**：传感器记录展示功能中冒泡排序条件写反，导致输出时间顺序与需求相反。

**【现象】**：需求要求最新记录显示在最上方（时间倒序），但实际运行中记录列表从旧到新输出，最早的记录排在第一位，最新的记录排在最后，与需求完全相反。

**【排查与原因】**：`display_latest_records` 和 `display_field_all_records` 中，`compare_timestamp(ts1, ts2)` 函数在 ts1 比 ts2 新时返回 1，ts1 比 ts2 旧时返回 -1；而冒泡排序的交换条件写为 `if (compare_timestamp(c->timestamp, c->next->timestamp) < 0)`，即当前节点时间早于下一节点时才交换，最终排序结果是时间从旧到新升序排列，与需求的倒序相反。此外原始链表采用头插法，新记录本就位于链表头部，代码额外复制链表再排序属于冗余操作。

**【解决方案】**：修正冒泡排序的交换条件，将 `< 0` 改为 `> 0`，使排序结果为时间倒序；或者更简单地，直接利用头插法链表本身的有序特性，无需复制临时链表和排序，直接遍历原始链表输出即可，既节省内存又避免排序 bug。

**【经验总结】**：编写排序逻辑时必须明确比较函数的返回值含义和排序目标方向，写完后应用小样本验证排序结果；如果数据结构本身已经保证了所需顺序，应直接利用而非重复排序，避免引入不必要的 bug。

## 问题五：内存分配失败分支缺少返回导致野指针

**【问题】**：`create_monitor_system` 函数中内存分配失败后缺少 return 语句，函数继续执行并返回野指针。

**【现象】**：当 `malloc` 分配 `fields` 数组失败时，程序打印错误信息并释放 `sys` 指针，但函数没有立即返回，而是继续执行后续代码，最终返回一个已被释放的野指针，调用方使用该指针会导致程序崩溃或未定义行为。

**【排查与原因】**：`create_monitor_system` 中 `sys->fields` 分配失败的分支内，执行了 `free(sys)` 和 `sys=NULL`，但函数末尾没有 `return NULL`，控制流会继续向下执行后续的初始化代码；由于 `sys` 已被置为 NULL，后续对 `sys->field_count` 等字段的访问本身就是空指针解引用，即使没有崩溃，函数返回值也是不可预测的野指针。

**【解决方案】**：在 `free(sys)` 之后立即添加 `return NULL`，确保内存分配失败时函数正确返回空指针；同时检查其他函数中类似的 malloc 失败分支，确保所有分配失败路径都有正确的返回语句，且已分配的资源得到释放。

**【经验总结】**：内存分配失败是必须处理的异常场景，每个 malloc 分支都应确保失败时正确返回并释放已申请资源；编写错误处理分支后要检查控制流是否会意外穿透到后续代码，必要时用 return 或 goto 统一错误出口。

## 问题六：添加田块功能硬编码测试数据

**【问题】**：实验田管理的"添加新田块"功能不支持用户手动输入，直接硬编码添加 5 条测试数据。

**【现象】**：用户在主菜单选择"1. 添加新田块"后，程序没有提示用户输入田块名称和负责人，而是直接一次性添加 5 条写死的测试田块数据，用户无法自定义新增田块的信息，交互逻辑与菜单选项的语义不符。

**【排查与原因】**：`field_management` 函数的 case 1 分支中，直接连续调用了 5 次 `add_field`，参数均为代码中写死的字符串常量（如"一号田"、"张三"等），没有调用 `scanf` 或其他输入函数接收用户输入；该分支原本可能是为了快速初始化测试数据，但被错误地放在了"添加新田块"的菜单项下，替代了正常的用户交互流程。

**【解决方案】**：修改 case 1 分支的逻辑，先提示用户输入田块名称和负责人，使用 `scanf` 或 `fgets` 接收用户输入，再调用 `add_field` 添加用户自定义的田块；可以另外增加一个"初始化测试数据"的隐藏选项或单独的初始化函数，用于开发测试，但不应放在正常的添加功能中。

**【经验总结】**：测试数据初始化逻辑应与正常业务功能分离，不能为了开发方便而用硬编码数据替代用户交互；菜单选项的语义必须与实际执行的功能一致，避免用户操作预期与实际结果不符。

## 问题七：非数字输入导致程序死循环

**【问题】**：菜单输入未做容错处理，用户输入非数字字符时程序陷入死循环。

**【现象】**：在各级菜单中，如果用户输入字母或其他非数字字符，程序不会提示输入错误并重新等待输入，而是不断重复打印菜单提示，陷入无限循环，只能强制终止程序。

**【排查与原因】**：所有菜单输入均使用 `scanf("%d", &choice)` 读取整数，当用户输入非数字字符时，`scanf` 匹配失败，返回 0，且输入缓冲区中的非法字符不会被消耗，一直留在缓冲区中；下一次循环再次调用 `scanf` 时，又读取到同一个非法字符，再次失败，如此反复形成死循环；代码中没有检查 `scanf` 的返回值，也没有在匹配失败时清空输入缓冲区。

**【解决方案】**：检查 `scanf` 的返回值，当返回值不等于 1（即未成功读取一个整数）时，使用 `while(getchar() != '\n')` 清空输入缓冲区，然后提示用户输入无效，请重新输入；可以封装一个统一的安全读取整数的函数，在所有菜单输入处调用，避免重复编写容错代码。

**【经验总结】**：用户输入是不可靠的，所有基于 `scanf` 的输入都应检查返回值；处理输入失败时必须清空缓冲区中的残留数据，否则会导致无限循环；交互式程序应封装统一的输入处理函数，集中处理容错逻辑。

## 问题八：按负责人搜索田块的错误提示文案错误

**【问题】**：按负责人搜索田块功能中，未找到结果时的错误提示文案复制粘贴错误。

**【现象】**：用户选择按负责人搜索田块，输入一个不存在的负责人姓名后，程序输出的提示信息为"未找到名称为xxx的田块"，而实际搜索维度是负责人，提示文字与实际操作不符，容易误导用户。

**【排查与原因】**：`search_fields_by_manager` 函数中，未找到匹配田块时的 `printf` 语句直接复制了按名称搜索函数中的提示文案，没有将"名称"修改为"负责人"，属于典型的复制粘贴后未完整修改的 bug。

**【解决方案】**：将 `search_fields_by_manager` 中未找到时的提示文案修改为"未找到负责人为xxx的田块"；同时全局检查其他函数中是否存在类似的复制粘贴错误，确保所有提示文案与实际功能一致。

**【经验总结】**：复制粘贴代码后必须仔细修改所有相关的字符串提示和变量名，不能只改逻辑部分；可以通过代码审查或统一的提示文案常量来减少此类低级错误。

## 问题九：趋势分析函数定长数组存在越界风险

**【问题】**：`analyze_trend` 函数使用固定大小数组存储温度记录，当田块记录数超过 100 条时发生数组越界。

**【现象】**：当某个田块的传感器记录数量超过 100 条时，调用趋势分析功能会向大小为 100 的固定数组中写入超过 100 个元素，导致栈内存越界，可能引发程序崩溃、数据损坏或其他未定义行为。

**【排查与原因】**：`analyze_trend` 函数内部定义了 `float temp_array[100]` 固定大小数组，遍历该田块的所有记录链表时，无条件地将每条记录的温度值存入数组，没有对数组下标做边界检查，当记录数超过 100 时继续写入，造成栈内存越界。

**【解决方案】**：改用动态分配（按记录数 `malloc`）或直接遍历链表计算趋势，避免固定大小数组；若必须使用数组，写入前需检查下标是否越界、超出容量时动态扩容，从根源上消除越界风险。

**【经验总结】**：固定大小数组是隐患来源，数据量不固定的场景应使用动态结构或在写入前做边界检查；栈上定长数组的越界不会在编译期暴露，应主动预估数据规模上限。
